2. ALTA — "stop" podía matar procesos ajenos (PID reutilizado)
   Solución : El archivo PID guarda "pid starttime binario". Antes de señalar
              se exige: PID numérico, starttime igual al de /proc/<pid>/stat y
              /proc/<pid>/exe == binario esperado. Si no coincide, se borra el
              archivo y NO se mata nada. Lock con flock: no hay dos start/stop
              a la vez (los servicios no heredan el fd del lock: 9>&-).
   Dónde    : cerberus.sh (owned_pid, stop_service, acquire_lock)
   Verificado: PID apuntando a un "sleep" -> sigue vivo tras stop.

3. ALTA — Reclamo de alertas no atómico (entregas duplicadas con 2 instancias)

              next_retry_at a now+lease (vencimiento). Otra instancia ya no ve
              la fila como pendiente. El UPDATE final (SENT/FAILED/DEAD) exige
              next_retry_at == lease propio (token de propiedad); si se perdió
              el lease no pisa el estado. Si el proceso muere, se reintenta al
              vencer. Sin cambios de esquema.
              Garantía real documentada: AL MENOS UNA VEZ. Cada webhook lleva
              "Idempotency-Key: cerberus-delivery-<id>" para que el receptor
              descarte duplicados.
   Dónde    : alerter-go/internal/dispatcher/dispatcher.go (claimDueAlerts,
              markSent, markFailedOrDead, checkOwned)
   Tests    : audit_regression_test.go (TwoInstancesNeverDeliverTwice,

R1. MEDIA — Apagado de C con hilos todavía activos
   Problema : Tras SIGTERM se esperaban 5 s y se volvía aunque quedaran hilos
              usando SQLite; main() cerraba la base igual. Con la base
              bloqueada por otro proceso y 3 peticiones en curso, el apagado
              tardaba ~10 s y salía con 1. Al reproducirlo con el código
              anterior el proceso llegó a morir con SIGSEGV (uso tras cierre).
   Solución : Apagado en 4 pasos:
              1. Cierra el socket: no entran peticiones nuevas.
              2. Espera de gracia de 1,5 s para que terminen normalmente.
              3. Si quedan hilos, cerberus_interrupt(): marca la base como
                 cancelada (atómico) y llama a sqlite3_interrupt(). La espera
                 por bloqueo ya no usa PRAGMA busy_timeout sino un manejador
                 propio con el mismo presupuesto (5 s) que corta al instante
                 si se canceló. Toda ingesta posterior devuelve
                 CERBERUS_ERR_CANCELLED y el cliente recibe 503.
              4. Espera 3 s más. SQLite solo se cierra si no queda ningún
                 hilo. Salida acotada: si alguno no terminó, NO se cierra la
                 base (evita el uso tras cierre), se avisa por stderr y el
                 proceso sale con _exit(1). WAL mantiene la base consistente.
              Peor caso: ~4,5 s.
   Dónde    : ingestor-c/src/main.c (run_http_server, wait_for_workers,
              main), ingestor-c/src/ingestor.c (cerberus_interrupt,
              cancellable_busy_handler, cancelled_or),
              include/cerberus_ingestor.h (CERBERUS_ERR_CANCELLED)
   Tests    : test_audit_regressions.py
                - test_sigterm_cancels_workers_before_closing_db: base
                  bloqueada + 3 peticiones + SIGTERM -> sale con 0 en < 4,5 s,
                  las 3 reciben 503, integrity_check ok, nada a medio escribir.
                  Antes: código -11 (SIGSEGV) tras ~10 s.
                - test_sigterm_lets_inflight_requests_finish (sin bloqueo: < 1 s)
              test_ingestor.c: test_interrupt_cancels_blocked_ingest
   Verificado: ThreadSanitizer (3 corridas del escenario): sin avisos.
              Reproducción de la auditoría: 9,74 s / código 1 -> 1,52 s /
              código 0.
   No probado: la rama "_exit(1) sin cerrar la base" (hilo que no termina ni
              tras cancelar) no se puede provocar con los límites actuales
              (lectura de socket acotada a 2 s, SQLite cancelable). Es una
              red de seguridad.

R2. MEDIA — Go podía crear la base con 0644 (URIs y "mode=memory" en el nombre)
   Problema : Cualquier ruta con "mode=memory" contaba como memoria y toda URI
              "file:" se saltaba la política. Con umask 022:
              file:/…/uri.db -> 0644; archivo "mode=memory.db" -> 0644.
              Además el driver quita lo que va tras '?' en rutas normales,
              así que "x.db?_pragma=…" protegía un archivo que no se usaba.
   Solución : resolveDBTarget() interpreta la ruta igual que modernc/sqlite:
              - ":memory:" -> memoria.
              - Ruta normal: el nombre es literal (con "mode=memory" incluido);
                se corta en el primer '?' como hace el driver.
              - URI "file:": se parsea (url.Parse), se decodifica %XX, se
                distingue file:rel.db / file:/abs / file:///abs /
                file://localhost/abs. mode=memory o file::memory: -> memoria.
              La política 0600 se aplica al archivo REAL y a -wal/-shm/-journal.
              Se rechazan explícitamente: vfs=, mode=ro (o desconocido), mode
              repetido, host distinto de localhost, fragmento '#', y "file:"
              sin ruta (base temporal).
              mode=rw no crea el archivo (como SQLite) pero sí lo deja en 0600.
   Mismo fallo en C y Rust (encontrado al revisar, no estaba en el informe):
              - C abre SQLite SIN soporte de URI: "file::memory:" se trataba
                como memoria pero SQLite creaba un archivo real
                "file::memory:" con 0644 (reproducido). Ahora C solo acepta
                ":memory:" o rutas normales; "file:..." -> error DB_OPEN.
              - Rust (rusqlite abre con URI): "file:x.db" protegía un archivo
                literal "file:x.db" y SQLite creaba "x.db" con 0644. Ahora
                rechaza URIs "file:" (salvo file::memory:).
   Dónde    : alerter-go/internal/dispatcher/dispatcher.go (resolveDBTarget,
              ensurePrivateDBFile, tightenCompanionFiles),
              ingestor-c/src/ingestor.c (cerberus_init),
              search-rust/src/lib.rs (ensure_private_db_file)
   Tests    : reaudit_permissions_test.go (8 formas de ruta con umask 022,
              comprobando además que el esquema quedó en ESE archivo; DSN en
              memoria no crean archivos; DSN no soportados se rechazan sin
              crear nada; archivo previo 0644 abierto por URI queda 0600).
              test_audit_regressions.py (TestDatabasePathPolicy),
              audit_regression_test.rs (sqlite_uri_paths_are_rejected_...).

R4. MEDIA — stop perdía el control de un servicio si se reemplazaba su binario
   Problema : La propiedad dependía de que /proc/<pid>/exe coincidiera con la
              ruta del binario. Al recompilar con el servicio en marcha, Linux
              muestra "ruta (deleted)": stop salía con 0, borraba el .pid y
              dejaba el servicio vivo, ya sin forma de controlarlo.
              (El problema venía de antes de las correcciones anteriores.)
   Solución : - El registro pasa a "pid starttime dispositivo:inodo binario".
                El dispositivo:inodo se toma del ejecutable al lanzar y se
                compara con stat -L /proc/<pid>/exe, que sigue apuntando al
                mismo inodo aunque el archivo se haya reemplazado.
              - Al lanzar se espera (máx. 2 s) a que nohup haya hecho exec del
                binario antes de guardar el registro.
              - Cuatro estados del registro:
                  owned    vivo + mismo starttime + mismo inodo -> se detiene
                  stale    proceso inexistente o starttime distinto (PID
                           reutilizado) -> se borra el registro, no se mata nada
                  unproven vivo con ese starttime pero otro ejecutable -> NO se
                           mata, se CONSERVA el registro y stop sale con 1
                  none     no hay registro
              - stop: si tras SIGTERM y SIGKILL el proceso sigue vivo, se
                conserva el registro y se informa un fallo. stop devuelve 1 si
                algún servicio falló (sigue intentando con los demás); restart
                no arranca si stop falló.
              - start se niega a lanzar un segundo servicio si su registro está
                en estado unproven.
              - status muestra "sin propiedad acreditada" en ese caso.
              - Registros del formato antiguo (pid starttime ruta) se siguen
                aceptando, comparando por ruta.

              stop_service, cmd_stop, cmd_status)
   Tests    : tests/test_launcher.py (TestStopOwnership)

R4b. MEDIA — Registros PID antiguos fallaban con espacios en la ruta
   Problema : pid_state() leía el registro con "read -r pid start ident exe":
              en el formato antiguo ("pid starttime ruta") una ruta con
              espacios se partía entre ident y exe, y la condición de
              compatibilidad exigía exe vacío. Resultado: stop salía con 1 y
              dejaba vivo un servicio iniciado por el lanzador anterior. Afecta
              justo a la ubicación real del proyecto
              (".../Carpeta principal/Juan Cruz/...").
              (No se mataba nada ajeno y el registro se conservaba.)
   Solución : Se lee la línea completa (IFS= read -r) y se separa con
              expresiones regulares: primero PID y starttime; el RESTO de la
              línea se conserva entero. Si empieza por "dispositivo:inodo "
              seguido de una ruta absoluta -> formato actual; si empieza por
              "/" -> formato antiguo (la ruta completa, con espacios);
              cualquier otra cosa -> registro ilegible (obsoleto, no se mata
              nada). La ruta se guarda siempre al final del registro.
   Dónde    : cerberus.sh (pid_state)
   Tests    : tests/test_launcher.py

     (exacto); Go acepta además URIs "file:" (sin vfs, modo rw/rwc/memory).
   - Un servicio en estado "sin propiedad acreditada" requiere revisión
     manual: el lanzador no lo mata ni borra su registro.
   - El lanzador usa /proc y flock: requiere Linux.
   - La E2E simula las peticiones del navegador; no ejecuta un navegador real.
